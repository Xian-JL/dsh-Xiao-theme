# Xiao 1.3.0 升级规格

日期：2026-10-18（Asia/Shanghai）。本文件替代 V2_OPTIMIZATION.md 中与本次升级冲突的旧建议，作为本次代码与验收依据。开发验证已完成；用户后续授权 GitHub prerelease / npm next 发布并通过 npm 安装，最终执行结果单独记录。

本次继续开发后的配套验收候选：**Xiao 1.3.0-rc.1 / Kinich 2.0.3-rc.1**。先前复用 2.0.2 的隔离包只保留为历史测试证据，新候选不复用已发布版本号；正式目标版本须在验收后确认。

## 1. 环境与范围

- 目标宿主为本机 DSH **0.2.1-rc.2**，不是稳定版。声明范围维持 `>=0.2.0-rc.2 <0.3.0`；不将声明范围内所有版本称为已实测。
- Xiao 正式目标版本 1.3.0，当前验收候选为 1.3.0-rc.1。Kinich 配套候选为 2.0.3-rc.1：新增主题总开关、互斥设置边界、条件品牌注册及关闭视觉层。历史隔离的 2.0.2 本地测试构建不是 npm 上已发布同版本；新候选已使用新版本号。
- 不增加远程图片或字体，不移除已有立绘、伙伴、粒子、点击风痕、呼吸、视差、会话反馈或余额能力。
- 本轮不使用 Computer Use，不把模拟测试、宿主启动或清单检查当作桌面视觉验收。

## 2. 强制主题互斥

### 2.1 用户操作

- 同一 Profile 内最多显示一个完整主题。两者可以同时安装，不能同时开启视觉层。
- 两边设置页都有主题总开关。开启 A 时，必须先成功保存 B 的 `enabled=false`，再保存 A 的 `enabled=true`。
- 只允许跨主题修改对方的 `enabled` 字段；不能清除或更改对方壁纸、历史、参数、立绘、动效偏好、位置或余额偏好。
- 关闭 A 不自动开启 B。两者都关闭时恢复 DSH 原生主题与品牌。
- 对方不存在时，当前主题可单独开启。
- 对方关闭失败、只读或写入拒绝时，不能继续开启当前主题，显示现有设置写入失败与重试反馈。
- 若对方已成功关闭，而当前主题开启失败，允许两者都关闭，不为恢复旧主题而引入反向竞态；用户可以重试。
- 单个主题中的连续写入依次执行。跨窗口或同时开关造成短暂配置冲突时，客户端有效视图固定最多展示一个，宿主随后持久化修复。

### 2.2 旧数据、重启及原生配置编辑

- 启动时旧配置两者都开着，固定保留 Kinich、关闭 Xiao；不依赖注册顺序或随机时序。
- 已有唯一开启主题时重启，保持该选择；两者都关闭时不强行开启任何一个。
- 宿主监听公开 `settings/document-updated`，通过 `describe` 和带 revision 的 `mutate` 修复冲突。已观察到明确从关闭变开启的主题优先；无法判定先后时仍使用 Kinich 作为固定优先项。
- 宿主写入错误记录日志，不无限重试；客户端视觉互斥仍生效。下次相关配置变更可再次尝试。
- 旧 Kinich 没有主题总开关时视为占用主题：Xiao 不展示、不能假装成功关闭旧 Kinich。必须先升级配套 Kinich，或在市场停用旧 Kinich 后再开启 Xiao。
- 外部文本编辑可能先把两个原始布尔值写成 true；客户端不能同时展示两者，宿主把配置收敛到单选状态。该机制不是跨命名空间的数据库事务。
- 本策略由 Xiao Host 提供持久化协调，两个配套 Client 提供有效视图与写入顺序约束。不能保证篡改代码、卸载协调器或继续使用两份旧包后的行为。

## 3. 关闭与资源归属

- Xiao 关闭时不再覆盖主题令牌或绘制背景，欢迎页原生标题与输入框恢复原布局。
- Xiao 的原生 DOM 样式必须同时要求主题开启及对应欢迎组件存在；页面阶段观察器在关闭时断开，重新开启时重新初始化阶段。
- 两边的侧栏图标、侧栏名称、欢迎页品牌插槽均随有效开关注册、释放；不能仅隐藏自定义图标后继续占用插槽。
- Kinich 关闭时卸载整个视觉内容子组件，释放其令牌、body 属性、壁纸呈现及视觉组件拥有的订阅/计时器；完整设置页仍可用于重新开启。
- 不删除 Profile 持久数据；再次开启恢复原有选择及动效偏好。

## 4. Xiao 背景与强调色

| 操作/值 | 背景图 | 已存图片与参数 | 自动强调色 |
| --- | --- | --- | --- |
| 主题关闭 | 隐藏 | 保留 | 不应用 Xiao 强调色 |
| 背景开关关闭 | 隐藏，工作区不因背景变透明 | 保留 | 仍由独立自动强调色开关控制 |
| 可见度 0 | 完全隐藏，恢复实色工作区表面 | 保留 | 仍由独立自动强调色开关控制 |
| 背景开关开启且可见度 1–100 | 按保存值呈现 | 保留 | 开启自动强调色时应用保存的采色结果 |
| 关闭自动强调色 | 背景不受影响 | 保留采色值 | 恢复 Xiao 默认强调色 |
| 恢复默认背景 | 清除当前自定义图片及其采色值 | 只按既有清除动作处理；本次不新增历史库 | 默认强调色 |

- `backgroundEnabled` 默认 true，旧配置补缺字段，默认可见度仍为 75。
- 采色在导入图片时执行一次并保存；背景开关、明暗切换、可见度调整不重新采色。不改变成功、警告和错误语义颜色。
- 图片处理完成前离开设置页，丢弃过期结果，不在卸载后发起图片保存。
- 预览可以继续展示保存素材供用户识别；工作区是否显示按上述表格执行，不能把预览图误作活动背景状态。

## 5. 弹窗与菜单

- 设置弹窗、对话框、警告对话框、菜单、下拉列表和 popover 使用完全不透明的表面与内部背景令牌。
- 覆盖 `[role=dialog]`、`[role=alertdialog]`、`[aria-modal=true]`、`[role=menu]`、`[role=listbox]`、`[popover]`；包括挂在 body 上的 portal。
- 明暗两套实色来自 Xiao 基础色板。透明工作区令牌不能继承进入弹窗内部。
- 背景可见度 0–100、自动强调色开启/关闭时均成立；不能依赖特定背景图颜色掩盖透明问题。
- 不改动宿主焦点管理、关闭动作、键盘处理、导航或会话逻辑。

## 6. 宿主适配与调度

- DSH 的 `hero/active/settling` 阶段标记仍可用于本机版本。原生类名后缀样式仅集中存在于主题样式适配段；阶段识别及变化过滤集中在 `scene/phase-model.js`。
- 页面观察只订阅 `data-phase` 属性和结构变化；纯文本、流式消息的普通节点、主题自身装饰节点不触发全页阶段扫描。新增或移除包含宿主阶段标记的子树时重新检测，每动画帧至多执行一次。
- 宿主结构不匹配时回退到会话页装饰，不隐藏找不到对应欢迎组件的原生元素。
- 会话等待状态优先读取宿主可选 `useSessionStatus` 的 `pendingInteraction`，只接受 approval/question/plan-review，并按 sessionId 选择。错误优先于等待，等待优先于运行。
- 老宿主没有该 hook 时使用独立兼容组件，保持 React hooks 顺序；保留原有字段回退。
- 会话桥统一使用已有完整结束信号解析器；没有可靠成功信号时继续显示中性“已结束”。

## 7. 验收与发布边界

- 自动化必须覆盖：双向切换及顺序、拒绝/只读/旧包、并发单视觉层、品牌注册释放、Profile 独立、旧冲突修复和重启、图片保留、零值/关闭、明暗弹窗实色令牌、观察器过滤、主/后台会话隔离、等待状态与未知终态。
- 隔离本机 Profile 验证已完成的细节见 VALIDATION.md 与本地 ISOLATED_HOST_RESULT.json。未经执行的视觉检查不写成通过。
- 后续人工重点：两边开关连续切换、两者全关原生欢迎页、关闭/重开和重启、背景 0/75/100 与独立开关、浅深设置弹窗和下拉菜单、真实审批/提问/停止/失败会话。
- 用户已追加授权发布 GitHub prerelease / npm next 并通过 npm 精确安装配套 RC；不得覆盖 latest。发布时必须同时交付 Kinich 配套版本，不能复用已发布版本号覆盖 npm 包。安装前备份并核对配置与壁纸数据，发布/安装结果不得冒充桌面视觉验收。
